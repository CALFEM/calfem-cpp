● I've read through the current code, ObjectiveFrame's use of it, your earlier
  calfem_cpp experiment, and calfem-python (cloned into the scratchpad). Here's
  the plan.

  What exists today

  - This repo: one header and one source file (~860 lines). It has bar3e/s,
    beam3e/s, assembly, solveq/spsolveq and SparseSolver. There is no build
    system and no git. calfem.cpp still includes <ofsolve/calfem.h>, so it won't
    compile on its own.
  - ObjectiveFrame: its src/ofsolve/calfem.* is identical to this copy. It uses
    beam3e/s, bar3e/s, spassem, extractAllDofs, toZeroIndex and SparseSolver
    (setup/solve/recompute, held by value). It builds with C++20 and depends on
    1-based edof/bcDofs.
  - Your earlier calfem_cpp: it already has bar2e/s and beam2e/s written in a
    tuple-returning style. It also has Geometry (points and lines only) and
    CDT/CGAL mesh generators. Some of this can be reused.
  - calfem-python: about 60 element and solver routines in core.py, a full
    Geometry class (splines, B-splines, circles, ellipses, surfaces, volumes,
    markers), GmshMeshGenerator, which writes a .geo file, runs gmsh and parses
    the result, and helpers in utils.py such as apply_bc, apply_force, and
    saving and loading meshes.

  Bugs in the current code that need fixing before anything is built on it:
  - solveq (dense) ignores the boundary conditions. bcDofsVec is never filled.
  - extractAllDofs needs bcDofs to be sorted (it uses std::set_difference) but
    doesn't sort them.
  - assem only fills the upper triangle of K.
  - SparseSolver::solve and recompute append to m_bcDofsVec on every call. The
    class also keeps raw pointers to K and bcDofs, which can dangle.
  - Missing includes: <map>, <algorithm> and <iterator>.
  - std::cout debug output is printed throughout the solvers.

  Phase 0: Make it a standalone library (do this first)

  1. Run git init and add .gitignore, a license file (LGPL-2.1, matching the
     headers), README and CLAUDE.md.
  2. Add CMake with a calfem target and a calfem::calfem alias, vcpkg.json
     (Eigen only for now), CMakePresets.json, and install/export rules so that
     find_package(calfem) works.
  3. Fix the include path to <calfem/calfem.h> and add the missing includes.
  4. Target C++17 as the minimum (structured bindings and std::optional). That
     makes it usable from ObjectiveFrame's C++20 and from elsewhere.
  5. Add a test framework (Catch2 or GoogleTest via vcpkg) and CI (GitHub
     Actions on Windows and Linux).

  Phase 1: Freeze ObjectiveFrame compatibility

  1. Write a compatibility test that exercises exactly the symbols and
     signatures ObjectiveFrame uses, including the 1-based conventions. This
     test must never break.
  2. Fix the bugs above without changing any signatures. Replace std::cout with
     an optional log callback that is silent by default.
  3. Connect ObjectiveFrame to the new library through a git submodule plus
     add_subdirectory, or FetchContent. Then link ofsolve against calfem::calfem
     and reduce include/ofsolve/calfem.h to a single #include
     <calfem/calfem.h>. Delete ObjectiveFrame's copied calfem.cpp.
  4. Run ObjectiveFrame's beam and bar solver results before and after the
     switch and compare them.

  Phase 2: Restructure for growth

  Split the single file into modules, with calfem.h as an umbrella header so
  existing includes keep working:
  include/calfem/
    calfem.h          umbrella (includes everything, keeps legacy API)
    types.h           RowVec, ColVec, Matrix, IntMatrix, ...
    elements/         spring.h bar.h beam.h flow.h plane.h solid.h plate.h
    material.h        hooke, effmises
    assembly.h        assem, spassem
    solvers.h         solveq, spsolveq, red, statcon, eigen, SparseSolver
    dofs.h            create_dofs, coord_extract, extract_eldisp, apply_bc...
    geometry.h  mesh.h  io.h
    compat.h          camelCase aliases (extractElDisp, extractEdof, ...)
  API conventions. Python names become the primary API. Results come back as
  return values, so Python code translates almost line by line:
  Matrix Ke = bar2e(ex, ey, ep);                   // Python: Ke = bar2e(ex, ey,
  ep)
  auto [Ke, fe] = bar2e(ex, ey, ep, eq);           // Python: Ke, fe = bar2e(ex,
  ey, ep, eq)
  auto [a, r]   = solveq(K, f, bc_dofs, bc_vals);
  The existing functions that write into output parameters (used by
  ObjectiveFrame) stay as overloads. The 3D beam and bar routines keep their
  fixed-size Eigen fast paths. Indexing stays 1-based, as in CALFEM.

  Phase 3: Port the element routines in batches

  Build a reference-data harness first. A small Python script in tests/ calls
  calfem-python with fixed inputs and saves Ke, fe and es to JSON. The C++ tests
  then compare against those values within a tolerance. calfem-python already
  has tests/gen_example_outputs.py, which can serve as a starting point.

  Each batch should include the CALFEM manual examples (exs1 and onward) as
  runnable programs in examples/.

  Phase 4: Geometry and meshing

  1. Geometry: a port of calfem-python's geometry.py, with points, the curve
     types (spline, B-spline, circle, ellipse), surfaces with holes, structured
     surfaces and volumes, markers, element sizes and bounding_box_2d. Keep the
     same method names so Python scripts translate directly.
  2. Built-in structured mesher with no dependencies: rectangles and boxes (the
     equivalent of shapes.Rectangle) for quad, tri and hex elements. This gives
     a working geometry → mesh → solve example early.
  3. GmshMeshGenerator: same approach as Python. It writes .geo, runs the gmsh
     executable and parses .msh. It returns coords, edof, dofs, bdofs and
     element_markers.
  4. Optional built-in 2D triangulator, enabled with CALFEM_WITH_CDT, so simple
     cases don't need gmsh. It reuses the CDT generator from your earlier
     calfem_cpp.
  5. io.h: save and load meshes and arrays, and VTK export for viewing results
     in ParaView.

  Phase 5 (later)

  - Python bindings (nanobind), so the C++ library can be checked directly
    against calfem-python.
  - A sparse-first assembly path (a TripletList-based assem overload) for large
    continuum meshes.
  - A docs site.

  Decisions I'd make unless you say otherwise

  - Gmsh: run the executable rather than link the SDK. Linking the gmsh SDK
    (GPL) would conflict with the library's LGPL license, and calling the
    executable is how Python already does it. Linking the SDK could become an
    option later.
  - Python-style snake_case names as the primary API, with your current
    camelCase names kept in compat.h.
  - Submodule for the ObjectiveFrame integration, because it allows editing both
    repos side by side. A vcpkg port can come once the API settles.

  I'd start with Phases 0 and 1 together, since everything after depends on
  having a build, tests and a frozen ObjectiveFrame contract. Should I go ahead
  with that?

● solveq didn't work, and the dense assem it's normally used with didn't either.
  Both are fixed now, and all 12 tests pass in Debug and Release.

  What was wrong:
  - solveq ignored the boundary conditions. It never copied bcDofs into its
    internal list, so the prescribed values never reached the system of
    equations. In Debug, Eigen stopped with a matrix-size assertion. In Release
    there's no such check, so it would have produced wrong results without any
    error.
  - assem only filled the upper triangle of K. The dense solver reads the lower
    triangle, so assem + solveq gave wrong answers even with solveq fixed.
    ObjectiveFrame doesn't use assem, so changing it doesn't affect
    ObjectiveFrame.

  Fixes in calfem.cpp:
  - solveq now uses bcDofs, and bcDofs can be listed in any order: each value in
    bcVals stays matched to its DOF.
  - solveq sizes a itself, so the caller no longer has to.
  - solveq returns false if K isn't symmetric positive definite (for example,
    too few supports), instead of returning garbage.
  - assem now adds the full element matrix.

  New tests in test_solvers.cpp:
  - Cantilever with dense solveq: checks the tip deflection against PL³/3EI and
    the support reactions, and checks that it matches spsolveq.
  - Two springs in series: a non-zero prescribed displacement, with the boundary
    DOFs given in reverse order.
  - The three-bar truss from the example, assembled with assem: checks that it
    gives the same K, displacements and reactions as spassem + spsolveq.

  Still open: spsolveq and SparseSolver still need bcDofs in sorted order, and
  spsolveq still needs a sized by the caller. Those belong with the other Phase
  1 fixes.

  numbers of arguments from the old ones. ObjectiveFrame's calls therefore still
  pick the old versions. The new versions call the old code internally, so the
  results are identical; a new test file, test_python_style.cpp, checks this for
  every overload and pins the return types.

  bar1d2d.cpp, beam1d.cpp, beam2d.cpp), and the formulas shared between elements

  How it's checked against calfem-python
  - Generator: generate_calfem_python.py calls the Python functions with seeded
    random inputs, with and without the optional arguments. It saves 209 cases,
    plus the calfem-python version and commit, to calfem_python_reference.json.
  - Comparison: test_calfem_python.cpp calls the matching C++ version for each
    case and compares every output to a relative tolerance of 1e-10. It also
    fails if a function has no reference cases.
  - The test catches real errors: I changed one value by one part in a million
    and the test failed, naming the case and the output. Regenerating gave a
    byte-identical file.
  - ObjectiveFrame's 3D elements also match calfem-python: bar3e/s and beam3e/s
    came from ObjectiveFrame and had never been compared with Python. They
    match.
  - Reproducing the data: you need numpy and scipy, which I installed only in a
    scratch environment. The command is in the README.
  - New test dependency: nlohmann-json, in the vcpkg tests feature only.

  Where the C++ version deliberately differs from Python (each is documented in
  the headers):
  - Evaluation points: calfem-python computes them with np.arange, which
    sometimes produces one point too many and then crashes (for example nep=7 on
    some element lengths). Those cases were left out of the data. C++ computes
    i·L/(nep−1), which gives the same points whenever Python works.
  - nep below 2: C++ throws std::invalid_argument instead.
  - beam2de always returns (Ke, Me, Ce). C++ can't choose a return type at
    runtime, so Ce is all zeros when there's no damping. Python's leftover debug
    prints are not copied.
  - Loads: single loads are double and multi-component loads are RowVec,
    consistent with bar3e.

  calfem-python bug found: beam3e and beam3s crash when eo is a plain list
  ('list' object has no attribute 'T'); it has to be a numpy array. Worth
  reporting upstream.

  Decision for you: soli8s returns strain first, (et, es, eci). I followed

  Where C++ differs from calfem-python:
  - plants with one element and several load cases gives a result for every row.
    This is a calfem-python bug: it reads ed with the element index, so it
    returns the first case's result and zeros for the rest.
  - plani4e without eq returns only Ke, like every other routine. Python always
    returns (Ke, fe).
  - An invalid ptype or ir throws std::invalid_argument. Python returns None or
    prints a message.

  calfem-python also returns some vectors as rows or 1D arrays (e.g. plante's
  fe). Those are only shape differences, and the generator normalizes them for
  the comparison.

● Phase 4 is done. You can describe geometry as in calfem-python and mesh it
  without running any executable, using either the built-in mesher or,
  optionally, the Gmsh library in-process.

  Using it
  Geometry g;  // point, spline, bspline, circle, ellipse, surface (with holes),
  struct_surface, struct_volume, markers
  auto [coords, edof, dofs, bdofs, element_markers] = create_mesh(g, 3, 0.1, 2);
  MeshGenerator adds Gmsh's options and returns boundary elements.
  apply_traction_linear_element, left over from Phase 3, is in now too.

  Built-in mesher (always available, no GPL code)
  - 2D only: triangles (el_type 2) or quads (el_type 3).
  - Curves: divided by el_on_curve (with progression or bump grading) or by the
    point element sizes, with grading along the curve. Nodes lie exactly on
    circles and ellipses.
  - Structured surfaces: mapped (transfinite) meshes.
  - Other surfaces: CDT triangulation, size-graded interior points and
    smoothing. In the tests the minimum angle stays above 20°, and the elements
    cover the domain exactly.
  - Quads on unstructured surfaces come from splitting each triangle into three.
    They're valid but irregular. Use Gmsh for better quads.
  - Anything else (3D, other element types, Gmsh-only options) gives a clear
    error that names the Gmsh backend.

  Gmsh backend (CALFEM_WITH_GMSH, off by default)
  - How it works: the geometry is written as a .geo description exactly as
    calfem-python writes it, then meshed with the Gmsh library inside the
    process.
  - The vcpkg gmsh port can't be used: it's built without meshing and without
    the .geo reader. The backend uses the official Gmsh SDK instead, found
    through GMSH_ROOT, via its C-API wrapper, which works with any compiler.
  - Identical to calfem-python: for six test geometries, including a structured
    3D hex box, the C++ meshes equal calfem-python's: same coordinates, edof,
    bdofs and markers. The .geo text is compared with Python's in every build,
    even without Gmsh.
  - License: Gmsh is GPL. calfem-cpp stays MIT, but programs built with this
    option must follow the GPL when distributed. The README says so.

  Bugs fixed along the way
  - Gmsh initialization crash: gmsh::initialize needs a program name, and
    passing none crashed.
  - Unconnected node: I first returned every Gmsh node, including the hole's
    centre point. That point belongs to no element, which made the stiffness
    matrix singular. Now only nodes used by elements are kept, as in
    calfem-python.

  Example: mesh2d meshes a plate with a hole and solves it in plane stress.
  mesh2d mesh.svg 2 also writes the mesh as an SVG and uses triangles. The

  Before you build with Gmsh yourself
  - The build-gmsh and build-nomesh folders in the project are my test builds
    and can be deleted. build-gmsh points at a Gmsh SDK in a temporary folder
    that won't stay around.
  - To build with Gmsh, install the SDK (or pip install gmsh) and pass
